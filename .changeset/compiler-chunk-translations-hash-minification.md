Add hash minification to builds with `experimentalChunkTranslations`: the experimental `experimentalChunkTranslationsMinifyHashes` option, or the `GT_CHUNK_TRANSLATIONS_MINIFY_HASHES` environment variable. A message's hash is random, so it does not compress, and it is most of what a message costs a page beyond its text. With the option on, the call sites such a build splits by chunk or by module, `<T>` and `t` templates from `gt-react`, pass an id in place of their hash, and the translation files of chunks hold no key at all: each file lists its translations once, with the ids that read each, which makes the JavaScript and those files smaller.

An id is 8 characters that name the list of its chunk's messages, a `.`, and the place of its message in that list: `kR3_x0Qa.12`. The name is a digest of the hashes of the chunk's messages, in the order of the hashes, so an id still follows from content alone: the same id names the same message in every build, no build needs a table from another, and a page can read the translation files of any build. Every call site of a chunk repeats the name, so it compresses to little, and what is left of an id is a small number. A chunk's ids change only when the set of its own messages does, which changes the chunk anyway. A message that several chunks read has an id in each, and its translation is still in a file once: a file is `[translations, lists]`, where `lists` gives, for the list of each chunk, runs of a place in the list, the place of its translation in the file, and how many follow on from both. `gt-react/chunk-translations` reads such a file into an entry per id, so this needs a `gt-react` that does: compiled code imports that entry by names only such a `gt-react` exports, and the build fails on a missing export with one that does not.

The hash of a message does not change anywhere else: the translation files at `files.gt.output`, the unsplit file, `msg` and every call site whose hash is computed at runtime keep it, and a message that a `t` template and a `msg` share is found under both. A `t` template whose hash is computed when it runs, because its options or a value are not written at the call, reads by hash as well: the build keeps every compiled message with the same text and structure in the unsplit file under its hash too, whatever its options and the names of its values. It warns of the modules whose call sites it cannot say that of, as with `derive()`; there, a message that a compiled call site also reads renders its source text. The build fails when two different lists of messages would share a name, when an id is already a key of the translation files, and when a chunk reaches the output with a call site that was not given its id. It also fails without `experimentalChunkTranslations`, and with `_tagIds`, which writes what a `<T>` passes into the page for tools that read it as the hash. Off by default, and a build without the option is unchanged.
