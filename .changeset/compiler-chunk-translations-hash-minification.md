'@generaltranslation/compiler': minor

Add hash minification to builds with the experimental `experimentalSplitTranslations` option: `minifyHashes: true` in the option, or the `GT_MINIFY_HASHES` environment variable. A message's hash is random, so it does not compress, and it is most of what a message costs a page beyond its text. With hash minification on, the call sites such a build splits by chunk or by module, `<T>` and `t` templates from `gt-react`, pass an id in place of their hash, and the translation files of chunks hold no key at all: each file lists its translations once, with the ids that read each, which makes the JavaScript and those files smaller.

An id is 8 characters that name a list of messages of its chunk, a `.`, and the place of its message in that list: `kR3_x0Qa.12`. The name is a digest of the hashes of the list's messages, in the order of the hashes, so an id still follows from content alone: the same id names the same message in every build, no build needs a table from another, and a page can read the translation files of any build. Every call site of a list repeats its name, so the name compresses to little, and what is left of an id is a small number.

In a build that splits by chunk a chunk has one list, of all its messages, and its ids change only when the set of its own messages does, which changes the chunk anyway. In a build that splits by module, hash minification also decides which file holds a message: a message is assigned once for each chunk that reads it, to the entries and dynamic imports that reach its call site in that chunk. A route that reads a label of the entry, or of the layout it loads after, has its own copy of that translation in its own file, and the file every page starts with holds nothing for a chunk that loads later. A chunk has one list for each group of its messages that the same entries and dynamic imports fetch, so a shared chunk, which holds what the entry reaches next to what only some routes do, has several. A translation file so names only lists that are wholly in it, of chunks that load with it: it is rewritten when one of its own messages comes, goes or is translated anew, and not when a chunk that loads later changes. Groups merge into files afterwards, so a file can hold several lists of one chunk.

This has two costs. The translation of a message that several chunks read is in each of their files, once per file. And the lists of a chunk follow from the imports of the whole app, not from the chunk alone: when another entry or dynamic import comes to fetch some of a list's messages, as a new route does that imports one module of a shared chunk, or an import that moves, the chunk gets other ids, and with them another file name, although its own code is the same. Without a chunk import map the chunks that import it are renamed too. A chunk that only one entry or dynamic import reaches, as most route chunks are, has one list and does not change this way.

The `assignment` of `gt-chunk-translations.json` lists a message once for each chunk that reads it, as its hash and 8 characters that name the module that reads it there, so a build with hash minification keeps its files by `previous` only from a build that had it on too. A build that splits by module without hash minification still holds every message in one file.

A message that several chunks read has an id in each, unless they list it with the same messages, and a file holds its translation once: a file is `[translations, lists]`, where `lists` gives, for each list, runs of a place in the list, the place of its translation in the file, and how many follow on from both. `gt-react/chunk-translations` reads such a file into an entry per id, so this needs a `gt-react` that does: compiled code imports that entry by names only such a `gt-react` exports, and the build fails on a missing export with one that does not.

The hash of a message does not change anywhere else: the translation files at `files.gt.output`, the unsplit file, `msg` and every call site whose hash is computed at runtime keep it, and a message that a `t` template and a `msg` share is found under both. A `t` template whose hash is computed when it runs, because its options or a value are not written at the call, reads by hash as well: the build keeps every compiled message with the same text and structure in the unsplit file under its hash too, whatever its options and the names of its values. It warns of the modules whose call sites it cannot say that of, as with `derive()`; there, a message that a compiled call site also reads renders its source text. The build fails when two different lists of messages would share a name, when an id is already a key of the translation files, and when a chunk reaches the output with a call site that was not given its id. It also fails with `_tagIds`, which writes what a `<T>` passes into the page for tools that read it as the hash. In a build with the split off, `minifyHashes` and `GT_MINIFY_HASHES` are not read. Off by default, and a build without hash minification is unchanged.
