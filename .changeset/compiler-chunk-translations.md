Add the experimental `experimentalSplitTranslations` option (or the `GT_SPLIT_TRANSLATIONS` environment variable) for production builds of single-page apps on `gt-react` with Vite. The option is an object, and setting it turns the feature on: `experimentalSplitTranslations: {}`, unless its `enabled` is false. Without the option, `GT_SPLIT_TRANSLATIONS=true` turns it on. A key set in the option overrides its environment variable. One build then serves every locale without loading a locale's whole catalog: the build reads the translation files at `files.gt.output` and writes the translations of each JavaScript chunk into a JSON file per locale next to the chunk, named after the chunk with the locale and a token that changes whenever that locale's files do, so the files can be cached as immutable and no JavaScript file changes when a translation does. The entry chunk and its static imports share one file per locale, which a script added to `index.html` requests while the page is parsed, together with the files of the chunks the page preloads with `modulepreload` links; each dynamic import requests the files of the chunks it loads while they download and runs them once the files have arrived, so a module that reads a translation as it is evaluated gets it. Which files an import needs is in the entry's file, not in the JavaScript, so an import costs a page no more than without the option. A page in the default locale requests none. `<T>` and `t` templates from `gt-react` are split by chunk. The app's `loadTranslations` is not called in such a build, which takes it out of the options `initializeGTSPA` is called with, so the catalogs it imports are not chunks of the build and no JavaScript file names them: the translations of messages that are not split, such as `msg` and dictionaries, go into one more file per locale, which the page requests with the entry's file and gt-react reads as its catalog, and the build reports how many they are. The build also writes `gt-chunk-translations.json` into its assets directory, which lists the file of each chunk and locale and holds the startup script for apps that write their own HTML. The startup script is inline: under a Content Security Policy that allows no inline script it needs a nonce, which Vite's `html.cspNonce` puts on it, and where the policy blocks it, messages render the source text. Source maps are not kept accurate yet for the chunks the build rewrites after the bundler has rendered them: those that hold a dynamic import or the call that starts the app.

`naming: 'map'` in the option names each file by the locale and the hash of its own content alone instead (`gt.<locale>.<hash>.json`), with one small map per locale that the page requests first, which says which file is each chunk's and which files each dynamic import needs. A changed translation then renames only the file it is in and the locale's map, a change to JavaScript alone renames only the map, and the files of chunks are requested once the map has arrived. With the default naming a file is named after its chunk, so a change to JavaScript that renames chunks renames their translation files too: `map` is the naming for an app that deploys often.
