Make `paraglide-context` and `collectContext()` faster and lighter on memory, so that large projects finish: a run is about twice as fast on one core, a large project is analyzed on every core, and the syntax trees a run holds no longer grow with the project. `PARAGLIDE_CONTEXT_THREADS` sets the number of threads; `0` analyzes in the main thread. `PARAGLIDE_CONTEXT_MEMORY_MB` sets the memory the run plans for, in place of the machine's or container's. Metadata files are written in pieces, and only the lines around each usage are held: a project whose metadata is longer than the longest string Node holds no longer runs out of memory, and its metadata file can be read back. A barrel of many `export *` no longer makes a run quadratic, an outdir with one file per message is read at once, and Vue, Svelte and Astro components cost less. A Vue or VitePress file's generated code is no longer kept for the rest of the run. The metadata files are unchanged. Source files are now read at most 64 at a time. Before, on Node 24 and older, a project with more files than the process's open-file limit could leave usages out of the metadata files without a warning.

With the `cache` option (`paraglide-context --cache`), off by default, a run keeps what it found of each file in the `paraglide-usage-context` section of the project's `gt-lock.json`, which is committed: the next run, e.g. in CI, indexes again only the files that changed, and analyzes again only those and the files whose analysis read one. Without a lock file, or past 2 MB, it is kept in `node_modules/.cache/paraglide-usage-context.json`. Merging the lock file with `gt`'s merge driver takes a `gt` release that keeps the section.
